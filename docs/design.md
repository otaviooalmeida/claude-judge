# Design discussion

Status: design decisions agreed through Q23. Offline implementation is in place and tested. Paid API calls remain separately gated and have not been approved or run.

## Agreed scope

- Portfolio-quality exploratory benchmark targeting a role requiring the Anthropic Claude SDK, JavaScript/Node.js, prompt engineering, structured JSON output, and LLM response quality evaluation.
- $5 maximum total new money paid, including provider credit purchases; not merely consumed token cost. Verify funding requirements and any taxes before purchase.
- Modern JavaScript with ES modules, JSDoc, and Zod runtime validation.
- Local CLI and static results dashboard; no visitor-triggered inference.
- Official Anthropic SDK; no orchestration framework needed initially.
- Claude Haiku and Claude Sonnet are judges of the same frozen candidate responses. The proposed OpenAI/Luna comparison is dropped.
- Candidate A is generated by Haiku and candidate B by Sonnet. Both judge models evaluate the same frozen pairs, without seeing candidate model metadata. Model agreement is not ground truth.
- Score each candidate on correctness, relevance, and completeness using 0/1/2 anchors; include a boolean unsupported_claims flag, preferred candidate or tie, and one short explanation.
- Correctness anchors: 0 incorrect, 1 partly correct, 2 correct. Relevance: 0 off-task, 1 partly relevant, 2 relevant. Completeness: 0 major omissions, 1 minor omissions, 2 complete.
- Judges see the source passage and task requirements, but not the reference answer or human labels.
- Forty English-language source-grounded evaluation tasks with short original passages: ten factual QA, ten constrained summarization, ten structured extraction, ten insufficient-evidence tasks.
- Human independently checks references, scores both candidate responses, and chooses a preferred response or tie before seeing automated judgments.
- One annotator; report this limitation and do not claim human-human agreement.
- Two judge prompts: simple baseline and an explicitly anchored rubric. Develop on a separate small calibration set, freeze before final evaluation, publish both results.
- Save candidate responses and reuse them across judging experiments.
- Domain terminology belongs only in CONTEXT.md; implementation and experiment design belong here or in subsequent specifications.

## Agreed experiment

- Haiku 4.5 generates candidate A and Sonnet 4.6 generates candidate B for each task, using the same neutral prompt and temperature 0.7. Preserve natural ties; do not cherry-pick candidate pairs or deliberately request poor answers.
- Compare pinned judge models `claude-haiku-4-5-20251001` and `claude-sonnet-4-6` on exactly the same trials. Both use temperature 0 and omit extended thinking. Repeated evaluations still require fresh requests. Record generation settings separately.
- Compare candidate scores lexicographically: correctness first, then absence of unsupported claims, then completeness, then relevance. Equal rankings produce a tie. Apply this policy to human and automated evaluations.
- Keep the declared winner and compute the rule-derived winner locally; report contradictions instead of silently rewriting the judgment.
- Eight separate calibration tasks, two per category, with at most two prompt-revision rounds. Forty held-out evaluation tasks; 48 tasks total.
- Both judge prompts evaluate the same frozen inputs with identical settings.
- Repeatability: 40 pairs × 3 fresh identical evaluations × 2 prompts = 240 judge requests. The first repeat is also the baseline.
- Position sensitivity: 40 reversed pairs × 2 prompts = 80 judge requests.
- Verbosity sensitivity: 20 human-checked concise/expanded pairs of equivalent substantive content × 2 presentation orders × 2 prompts = 80 judge requests. These are controlled variants, not additional independent tasks.
- Total main experiment: 400 judge requests per model (800 across both models), excluding calibration. Human review includes the 20 verbosity pairs in addition to natural candidates and calibration work.

## Agreed dataset preparation

- The coding assistant drafts passages, tasks, reference checklists, and task-specific scoring guidance directly as repository files, without separate project API calls. The human independently checks and corrects them.
- Describe provenance as an AI-assisted, human-reviewed synthetic dataset, not an independently sourced benchmark.
- Select five held-out tasks per category for verbosity controls before seeing judge results. Draft expansions of saved candidates and have the human check substantive equivalence.

## Agreed measurements

- Headline human agreement uses the first trial per task and prompt: preferred-candidate agreement and Cohen's kappa. Analyze repeats separately.
- Score accuracy: per-criterion agreement and mean absolute error against human labels.
- Unsupported claims: confusion matrix against human flags.
- Repeatability: percentage of tasks with identical preferences across all three fresh identical trials.
- Position sensitivity: preference-change rate after reversal, mapped back to candidate identity.
- Verbosity sensitivity: longer-response wins, shorter-response wins, and ties.
- Internal rule adherence: declared versus rule-derived preference disagreement.
- Show denominators and task-level uncertainty where appropriate. Undefined statistics are unavailable, not zero. Category breakdowns are descriptive with ten tasks each.
- Record invalid, failed, or truncated judgments explicitly rather than silently replacing them.

## Agreed execution safeguards

- Offline fixtures by default. Paid execution requires an explicit flag and separate authorization.
- Batch processing for measured runs.
- Candidate A and B use temperature 0.7, with a maximum of 300 output tokens. Judge temperature 0, maximum 400 output tokens, extended thinking disabled.
- Conservative preflight estimates reserve maximum output allowances and account for outstanding work.
- Comparison usage ceiling: $5 total new cash. The full planned Haiku + Sonnet comparison is estimated at approximately $2.7464 before unmodeled overhead; rerun the plan and inspect provider billing before execution.
- Save batch identifiers immediately; resume recorded jobs rather than resubmitting them. Retrieval polls batch status until `ended` (up to 24 hours) before requesting the results URL.
- No silent replacement of failures and no automatic paid JSON repair. Any retry must be bounded, budgeted, and linked to its original trial.

## Agreed portfolio deliverables

- Static dashboard built from saved results without an API key or visitor-triggered inference.
- Findings: Haiku versus Sonnet, baseline versus improved prompt, uncertainty, actual API cost.
- Bias and stability: position, verbosity, repeated evaluation.
- Case explorer: source passage, candidates, human labels, judgments.
- Methodology: frozen prompts, model settings, dataset provenance, limitations.
- Concise README, architecture diagram, reproducible commands, fixture-based CI.

## Implementation defaults proposed earlier

- JSONL data and results, local analysis, static HTML tables, and Vitest fixture-based tests. CSV export can be added after measured results exist; these are lightweight implementation choices, not additional experiment conditions.

## Cost caveat

The offline plan estimates 48 Haiku candidate generations, 48 Sonnet candidate generations, and 416 judgments for each judge model. Mixed candidate generation plus Haiku judging is approximately $0.8336; the full Haiku + Sonnet comparison is approximately $2.8304 under the current token assumptions. These are planning estimates, not quotes or authorization. Actual input lengths, structured-output overhead, retries, and generation of verbosity controls may change them. Total cash outlay includes funding minimums and taxes; verify these before purchase. No other provider is planned.
